# 首页「视频监控」跳转与后端联动落地方案

## 1. 文档目标

基于当前工程现状，设计一套可直接落地的“首页点击视频监控按钮 -> 进入视频监控页 -> 加载监控概览 -> 进入实时播放”的完整技术方案。

本方案严格遵循以下原则：

- App 端只负责页面跳转、标准接口调用、数据解析、状态渲染、异常提示。
- 所有核心业务逻辑统一收口到后端，包括权限校验、项目范围校验、摄像头状态判断、视频流地址分发、编码兼容策略、资源调度、播放会话管理。
- 方案优先复用当前 `workerM` 和 `workerback` 已有结构，不做脱离现有工程的大重构。

## 2. 当前工程基线

### 2.1 Android 现状

当前已经存在如下基础能力：

- 首页入口：`app/src/main/java/com/qkzc/workerm/ui/home/HomeFragment.kt`
- 视频首页：`app/src/main/java/com/qkzc/workerm/ui/video/VideoHomeActivity.kt`
- 视频直播页：`app/src/main/java/com/qkzc/workerm/ui/video/VideoLiveActivity.kt`
- 会话存储：`app/src/main/java/com/qkzc/workerm/data/session/SessionStore.kt`
- 网络封装：`app/src/main/java/com/qkzc/workerm/data/network/ApiClient.kt`
- 统一接口定义：`app/src/main/java/com/qkzc/workerm/data/network/SupervisorApi.kt`

已存在的跳转雏形：

- `HomeFragment` 中 `binding.videoAction.setOnClickListener { startActivity(Intent(requireContext(), VideoHomeActivity::class.java)) }`
- `VideoHomeActivity` 当前只是静态页面，点击卡片后直接进入 `VideoLiveActivity`

现状问题：

- 首页按钮没有加载态、点击防抖、失败降级逻辑。
- 页面跳转没有携带标准化上下文参数。
- `VideoHomeActivity` 和 `VideoLiveActivity` 目前没有真实后端联动。
- `SupervisorApi` 中尚无视频监控域接口。
- 当前项目没有接入 `Media3/ExoPlayer`，尚不具备真实视频播放能力。

### 2.2 后端现状

当前后端已经具备以下可复用基础：

- 管理端项目范围校验：`workerback-manage/.../ManagerProjectAppController.java`
- 首页总览接口：`workerback-manage/.../ManagerHomeAppController.java`
- 登录用户解析与管理端身份判定：`SecurityUtils.getLoginUser()` + `RequestApprovalSupport.isManageUser(user)`
- 管理端 App 接口风格：统一走 `/app/manage/**`

现状问题：

- 后端暂无视频监控域 App 接口。
- 后端暂无摄像头资源、播放会话、播放授权、设备状态聚合能力。
- 当前错误返回仍以 `code/msg/data` 为主，视频业务缺少细粒度错误码。

### 3.5 风险点

1. 当前 `minSdk = 33`

- 这意味着当前安装包只支持 Android 13 及以上。
- 若业务要求覆盖 Android 8-12 主流设备，则需要单独安排兼容性专项，不能只开发视频页。

2. 当前无播放器依赖

- 如果不引入 `Media3`，无法稳定承接 HLS/RTSP 等视频流。

3. H.265 兼容性不是百分百

- 不同厂商设备对 H.265 硬解支持差异较大，必须由后端提供 H.264 回退能力。

4. 视频流不能直接暴露固定地址

- 否则存在越权访问、地址泄露、长期有效链接被转发等安全风险。

## 4. 总体技术方案

## 4.1 结论

当前“App 纯前端直接调用后端普通接口”的架构思路本身可行，但对于视频监控场景还不够稳。

推荐升级为：

```text
App
  -> 管理端 App BFF 接口(/app/manage/video/**)
  -> 视频监控域服务
  -> 第三方视频平台/国标平台/自建流媒体网关
```

说明：

- App 仍然只调用自家标准化后端接口，不直接对接第三方视频平台。
- 后端增加一层“视频聚合域/BFF”，统一做权限、调度、协议选择、流地址签发、设备状态聚合。
- 这是对当前架构的增强，不是推翻重做。

## 4.2 前后端职责划分

### App 端职责

- 处理首页按钮点击、防抖、加载态和跳转。
- 读取本地 `SessionStore` 中的登录态和当前项目上下文。
- 组装非敏感页面参数并传入视频页。
- 请求后端视频接口并渲染结果。
- 调用播放器播放后端返回的视频配置。
- 处理网络异常、接口超时、权限不足、播放失败提示。

### 后端职责

- 根据 token 识别用户和项目管理范围。
- 校验菜单权限、按钮权限、项目范围、设备范围。
- 判断摄像头在线状态、维护状态、是否被禁用。
- 根据 App 上报的能力信息选择协议、分辨率、编码格式。
- 生成短时效播放地址或播放票据。
- 管理播放会话、心跳、并发数、资源调度、审计日志。

## 4.3 为什么不建议把 token 通过 Intent 明文传递

用户要求跳转时可携带必要参数，但敏感信息不建议直接通过页面参数传递。

推荐做法：

- 通过 Intent 传递：`projectId`、`projectName`、`entrySource`、`requiredPermissionCode`、`launchTraceId`、`cameraPermissionState`
- 不通过 Intent 传递：`accessToken`、`refreshToken`
- token 统一从 `SessionStore` 或网络拦截器读取

原因：

- 避免 token 被日志、崩溃堆栈或调试工具意外采集。
- 避免页面间传值链路变成安全漏洞。
- 保持和当前 `SessionStore` 设计一致。

## 5. Android 端落地方案

## 5.1 首页按钮交互设计

目标：保证首页点击“视频监控”后体验稳定，不重复跳转，不空白闪屏。

### 交互规则

1. 点击前校验

- 登录态存在
- 已选择项目，若未选择则优先回退到 `SessionStore.projectId`
- 网络可用

2. 点击中处理

- 对 `videoAction` 做 600ms 防抖
- 进入 loading 态，按钮置灰或显示小型进度态
- 生成 `launchTraceId`
- 构建 `VideoLaunchArgs`

3. 点击成功后

- 使用 `VideoHomeActivity.newIntent(context, args)` 启动目标页
- 目标页优先显示骨架屏，不等待接口返回后才绘制首屏

4. 点击失败降级

- 无网络：Toast + 保持原页面
- 无项目：弹窗提示“请先选择项目”
- 登录失效：跳登录页
- 启动异常：Toast“视频监控页面打开失败，请稍后重试”

## 5.2 页面间参数设计

建议新增 `VideoLaunchArgs`：

| 字段 | 类型 | 来源 | 是否敏感 | 说明 |
| --- | --- | --- | --- | --- |
| `projectId` | Long | `SessionStore` / 当前项目 | 否 | 当前项目 ID |
| `projectName` | String | `SessionStore` | 否 | 页面标题展示 |
| `entrySource` | String | 固定值 `HOME` | 否 | 记录来源页面 |
| `requiredPermissionCode` | String | 固定值 | 否 | 页面权限码，如 `VIDEO_MONITOR_VIEW` |
| `launchTraceId` | String | App 生成 UUID | 否 | 用于链路追踪 |
| `cameraPermissionGranted` | Boolean | 本地权限判断 | 否 | 若后续支持扫码/本机预览可复用 |
| `networkType` | String | 本地获取 | 否 | `WIFI/4G/5G/UNKNOWN` |

不建议放入 Intent 的字段：

- `accessToken`
- `refreshToken`
- 用户手机号
- 用户完整身份信息

## 5.3 视频首页页面状态机

`VideoHomeActivity` 建议增加以下页面状态：

- `Idle`
- `Loading`
- `Content`
- `Empty`
- `NoPermission`
- `NetworkError`
- `ServerError`

首屏加载流程：

```text
onCreate
  -> 解析 VideoLaunchArgs
  -> 读取 SessionStore
  -> 展示 Skeleton
  -> 调用 /app/manage/video/entry-context
  -> 校验页面权限、项目权限、默认筛选参数
  -> 调用 /app/manage/video/overview
  -> 渲染统计卡片 + Tab + 摄像头列表
```

## 5.4 视频直播页页面状态机

`VideoLiveActivity` 建议增加以下状态：

- `LoadingPlayConfig`
- `PreparingPlayer`
- `Playing`
- `Buffering`
- `Retrying`
- `PlaybackError`
- `Offline`
- `PermissionDenied`

直播页流程：

```text
进入页面
  -> 请求 play-session
  -> 获取短时效播放信息
  -> 初始化 Media3
  -> 开始播放
  -> 定时心跳 heartbeat
  -> 退出页面 close session
```

## 5.5 Android 推荐技术选型

在当前单模块项目下，推荐采用“局部增强，不全量重构”的方式：

- UI：继续使用 `Activity + ViewBinding`
- 页面状态：视频域新增 `ViewModel`，不强制全项目统一改造
- 网络：沿用 Retrofit + OkHttp
- 协程：沿用 `lifecycleScope`
- 播放器：新增 `androidx.media3`

推荐播放器依赖：

```text
androidx.media3:media3-exoplayer
androidx.media3:media3-ui
androidx.media3:media3-exoplayer-hls
androidx.media3:media3-exoplayer-rtsp
```

说明：

- HLS 兼容性最好，建议作为默认播放协议。
- RTSP 可作为部分设备直连或网关转发能力。
- 若后续有超低延迟需求，再评估 WebRTC 网关作为二期。

## 9. 异常处理机制

## 9.1 App 端兜底策略

### 首页入口异常

- 重复点击：防抖 + loading 防二次启动
- `ActivityNotFoundException`：Toast + 埋点
- `SessionStore` 无 token：跳登录页

### 视频首页异常

- 无网络：展示“网络不可用，请检查后重试”
- 接口超时：展示重试按钮，不自动连续重试
- 无权限：显示无权限页，并提供“返回首页”
- 模块未开通：显示空态文案
- 数据为空：显示空摄像头列表

### 直播页异常

- 播放地址过期：自动刷新一次播放会话
- 摄像头离线：展示离线状态，不拉起播放器
- H.265 不支持：提示后自动回退 H.264
- 播放器缓冲超时：切换备用地址
- 连续两次拉流失败：停止自动重试，提示人工重试

## 9.2 后端异常分类

建议在现有 `code/msg/data` 基础上新增 `bizCode` 与 `traceId`，兼容现有接口风格：

```json
{
  "code": 500,
  "msg": "当前账号没有视频监控权限",
  "bizCode": "VIDEO_PERMISSION_DENIED",
  "traceId": "0acdd640-c29d-4a8e-bc4e-413cf1a74ae1",
  "data": null
}
```

推荐错误码定义：

| bizCode | HTTP 语义 | 说明 | App 行为 |
| --- | --- | --- | --- |
| `AUTH_TOKEN_INVALID` | 401 | 登录失效 | 跳登录 |
| `MANAGE_SCOPE_DENIED` | 403 | 无项目管理权限 | 返回上一页 |
| `VIDEO_PERMISSION_DENIED` | 403 | 无视频模块权限 | 无权限页 |
| `VIDEO_MODULE_DISABLED` | 403 | 项目未开通视频 | 空态页 |
| `VIDEO_CAMERA_OFFLINE` | 409 | 摄像头离线 | 提示离线 |
| `VIDEO_CAMERA_DISABLED` | 409 | 摄像头已禁用 | 提示不可查看 |
| `VIDEO_DISPATCH_FAILED` | 500 | 流地址分发失败 | 可手动重试 |
| `VIDEO_VENDOR_TIMEOUT` | 504 | 第三方网关超时 | 提示稍后重试 |
| `VIDEO_CODEC_UNSUPPORTED` | 422 | 编码不兼容 | 回退 H.264 |
| `VIDEO_SESSION_EXPIRED` | 410 | 会话过期 | 自动续签一次 |

## 10. 超时与重试策略

## 10.1 App 接口超时建议

当前全局超时：

- `connectTimeout = 15s`
- `readTimeout = 20s`
- `writeTimeout = 20s`

视频域建议：

1. 入口上下文、概览、列表接口

- 连接超时：10s
- 读取超时：10s
- 自动重试：最多 1 次
- 重试条件：仅 `GET` 请求、仅网络抖动和超时

2. 创建播放会话接口

- 连接超时：8s
- 读取超时：10s
- 自动重试：默认不自动重试
- 说明：防止重复创建会话，若要重试必须带 `X-Idempotency-Key`

3. 心跳接口

- 超时：5s
- 不阻塞 UI
- 连续 2 次失败后仅提示“网络波动，正在尝试恢复”

## 10.2 播放失败重试策略

播放器内部建议：

- 主地址失败 -> 切备用地址
- 备用地址失败 -> 刷新 play-session 一次
- 仍失败 -> 停止自动重试，给出“点击重新播放”

## 11. 权限与安全管控

## 11.1 权限模型

视频监控建议采用双层权限：

1. 页面权限

- `VIDEO_MONITOR_VIEW`

2. 数据权限

- 项目范围权限
- 摄像头范围权限
- 特定区域权限，例如塔吊区、出入口、仓库区

后端必须强校验：

- token 对应登录用户
- 用户是否属于管理端角色
- 用户是否可管理该项目
- 用户是否有视频页面权限
- 用户是否有该摄像头查看权限

## 11.2 流地址安全要求

- 不向 App 返回长期有效的固定流地址
- 播放地址有效期建议 30-60 秒
- 地址必须带签名和过期时间
- 每次创建播放会话返回独立 `sessionId`
- 心跳超时或页面退出后，后端主动失效会话

## 11.3 敏感信息保护

- token 不放 Intent
- 直播页建议支持水印
- 涉及敏感项目可选开启防录屏 `FLAG_SECURE`
- 所有播放行为写审计日志：用户、项目、摄像头、时间、IP、设备 ID

## 12. 编码兼容性与稳定性策略

## 12.1 编码支持原则

- 优先支持 `H.264`
- 在设备明确支持时启用 `H.265`
- 后端根据 App 上报能力做最优选择
- 若 `H.265` 播放失败，自动回退 `H.264`

## 12.2 协议选择建议

- 默认：`HLS`
- 备选：`RTSP`
- 二期低延迟：`WebRTC`

建议后端按以下顺序分配：

```text
HLS(H.264) -> HLS(H.265) -> RTSP(H.264) -> RTSP(H.265) -> WebRTC(二期)
```

实际策略可根据业务调整，但原则是不把复杂判断留给 App。

## 12.3 当前工程兼容性说明

当前 `workerM` 的 `minSdk = 33`，因此严格来说只兼容 Android 13 及以上。

如果业务目标是“主流移动端系统版本”，建议拆成两步：

1. 当前阶段

- 先在现有包内落地视频监控功能
- 覆盖 Android 13-16 的正式环境

2. 兼容扩展阶段

- 将 `minSdk` 评估下调到 26 或 28
- 对扫码、通知、媒体播放、权限申请做回归验证

若短期无法下调 `minSdk`，则要在方案评审时明确：当前安装包不覆盖 Android 8-12 用户。

## 13. 性能优化要点

## 13.1 首页跳转性能

- 首页点击后立即进入目标页骨架屏，避免等待接口完成再跳转
- `VideoHomeActivity` 首屏只拉入口上下文和概览，不一次性拉全量摄像头详情
- 摄像头列表分页加载

## 13.2 视频页渲染性能

- 封面图使用压缩图
- 列表采用 `RecyclerView + DiffUtil`
- Tab 切换复用已有数据缓存，避免重复请求

## 13.3 播放性能

- 根据网络类型选择默认清晰度
- 后端可返回 `recommendedProfile = FLUENT/HD/FULL_HD`
- Wi-Fi 默认高清，移动网络默认流畅
- 心跳和状态轮询分离，避免高频接口调用

## 13.4 后端性能

- 摄像头状态建议使用缓存快照，不要每次列表都实时打第三方平台
- 流地址分发结果可做秒级缓存，但必须与权限绑定
- 统计接口和设备列表接口分离，降低单接口压力

## 14. 建议数据模型

若当前后端还没有视频表，建议最少具备以下模型：

- `video_device`
  - 摄像头主数据，包含编码、名称、区域、供应商、协议能力、状态
- `video_project_bind`
  - 项目和摄像头绑定关系
- `video_device_status_snapshot`
  - 在线状态、最后心跳、异常原因
- `video_play_session`
  - 播放会话、用户、项目、摄像头、开始结束时间、会话状态

## 15. 开发实施顺序

建议按四步落地：

### 第 1 步：首页跳转闭环

- 首页按钮防抖
- loading 态
- `VideoLaunchArgs`
- 失败降级

### 第 2 步：视频首页后端联通

- `entry-context`
- `overview`
- 摄像头分页列表
- 空态/错态/无权限态

### 第 3 步：直播播放闭环

- `play-session`
- Media3 播放器
- 心跳与关闭会话
- H.264/H.265 回退

### 第 4 步：稳定性增强

- `bizCode`
- 埋点
- 审计日志
- 设备状态缓存
- 压测与弱网专项

## 17. 最终落地建议

本需求最稳妥的落地方式不是“App 直接拼接视频地址跳播放”，而是：

1. 首页只负责稳定进入视频页
2. 视频页只负责标准 API 请求与渲染
3. 后端统一承担权限、资源调度、地址签发、编码回退、会话管理
4. 播放端使用 `Media3` 承接主流协议与编码

这样做能同时满足：

- 前端交互流畅
- 核心业务逻辑后端收口
- 编码兼容和异常兜底完整
- 安全性和可运维性更高

这也是最适合当前 `workerM + workerback-manage` 现有代码结构的增量落地路径。
